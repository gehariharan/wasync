# Threat model: agent access to wasync

Scope: the local wasync owner (TUI or `serve`), its loopback API, the `wasync query` CLI, and agent clients such as wasync-axi. See [ADR-001](ADR-001-repository-boundaries.md).

## Assets

- WhatsApp pairing credentials (whatsmeow session store)
- The SQLite archive: message bodies, media, chat membership, capture preferences
- Ability to act as the user on WhatsApp: send, react, edit, revoke, change chat or group state
- Legacy tokens (`api.token`, `send.token`, `approve.token`) and agent credentials

## Trust boundaries

| Boundary | Enforcement |
|---|---|
| Other machines → API | Literal loopback address only (`api.ValidateAddr`); Host and Origin checks against DNS rebinding and browsers |
| Other tailnet devices → web app (opt-in) | Off by default. With `tailnet.json` set by a human (typed word and system prompt), `tailscale serve` on this computer forwards HTTPS on the tailnet name to loopback. Only `/ui/` is served for that Host, only on the default HTTPS port and only with a single `Tailscale-User-Login` equal to the one allowed login, never via Funnel, and forms need the HTTPS tailnet origin. Sessions are bound to that login. Remote pages never raise the system prompt. See [Tailscale](../tailscale.md) |
| Other local users → data dir | Private file and directory permissions (`internal/localfs`, Unix modes and Windows ACLs) |
| Agent → wasync | Scoped agent credential checked by wasync on every `/api/v1` request; scopes, chat allowlist, rate limit, expiry; audit log |
| Agent → destructive actions | Not grantable; human approval queue; the owner asks the person at the computer to confirm (see "What the human check is, and is not") |
| Agent → approving its own request | The owner, not the caller, asks the person: Touch ID or the account password on macOS, Windows Hello on Windows. A signed request, a typed phrase or a click on the approval page is necessary but never sufficient where this check exists |
| Same OS user → archive | Not a boundary. `wasync query` offline reads are equivalent to the user reading their own files and are read-only |
| WhatsApp content → agent | Message text and contact or chat names are untrusted data; never rendered as instructions or hints |

## Threats and mitigations

| Threat | Mitigation |
|---|---|
| Agent instructed by message content (prompt injection) to send or delete | Writes need explicit scopes and allowlisted chats granted by a human in wasync; destructive actions are never grantable; AXI renders content as delimited data |
| Agent or skill passes flags to bypass confirmation | Flags are UX only; wasync enforces scopes server-side |
| Leaked agent credential | Hash-only storage, per-client revoke and expiry, rate limits, audit trail |
| Agent credential replayed on legacy routes, or legacy token on v1 | The two credential types are isolated; each route family accepts only its own |
| Legacy read token mutating capture policy (existing behaviour) | Recorded in the baseline audit; unchanged for compatibility; agent credentials do not inherit it |
| Duplicate WhatsApp session | Only wasync pairs; `device.lock`; AXI never connects to WhatsApp |
| Data loss on upgrade | Additive-only migrations, automatic pre-migration backup, schema upgrade tests from every released schema |
| Contact names in logs, or hostile names reaching an agent | Direct-chat names (address-book, push and business names) come from whatsmeow's contact store and events and are stored only in the local archive; they are never written to logs or diagnostics. Names are trimmed of control characters and capped at 256 characters when stored, shown in `wasync-axi` as sanitized `untrusted_` values, and visible to an agent only through the same `read.chats` scope and chat allowlist as the chat itself. Push names are chosen by other people, so a name can impersonate a contact or carry instruction-like text; agents must treat it as data, and a name is never an authorization input (allowlists use chat IDs). Residual risk: an agent with `read.chats` learns the owner's saved contact names for the chats it may see |
| Secrets or bodies in logs | Audit and diagnostics record identifiers and outcomes only |
| Change feed skipping events | Transactional journal with sequence cursors and an epoch; no timestamp cursors |
| Agent talks its way into a chat it was not given | By default access is never granted by asking. A request becomes a pending human approval (TUI dialog, the approval page, or `wasync actions approve` with a typed `ALLOW CODE`; 30-minute expiry that survives a restart, no replay, approve token separate from every agent credential). Where the computer has a system confirmation, the owner then asks the person to confirm with it, whichever way the approval arrived. The person sees which agent, which chat and whether read, send/reply/react or also edit-own, and picks the history depth before confirming. Approval enables capture for that one chat and adds a per-chat grant limited to scopes the credential already holds (read, send and edit are separate; capture, group and export scopes are never requestable). Rejection, expiry, a revoked agent or any failure changes nothing; grants and denials are audited |
| Agent floods the person with prompts, hides what it wants, or probes which chats exist | Rate limit, one prompt per agent and query, at most three unanswered per agent, 32 queued overall. The dialog shows wasync's resolved candidates, not text the agent supplied; the agent's query is shown as sanitized display text and chat names have control characters stripped. The reply to an access request is `pending` whether zero, one or many chats matched (a request that matched nothing is queued, shown to the person as "no chat matched", cannot be approved, and expires), and candidates are never returned, so asking reveals nothing about chats the agent was not given. Headless, `serve` announces each new request on its console and log with the agent name and request ID only; the chats appear only in `wasync actions list`, which needs an interactive terminal and the send credential |
| Owner picks "sync all chats" and an agent then misuses it | A deliberate, human-only trade-off: `wasync access mode all` (or the TUI setup screen / `M`, or the approval page) needs a typed `SYNC ALL` in a terminal where one is used, then the system confirmation where the computer has one, and the screen says plainly that agents can then discover and access any chat by name or number (a matching request is granted at once, so a name probe both reveals and grants that chat) and read, send, reply and react in any chat without asking; ask-each-time mode reveals nothing. It enables capture for all chats with the history depth the owner picks, and approves only requests for the one chat a request matched; edit-own and destructive actions stay manual, requests that match nothing or several chats still wait, and per-agent rate limits, expiry, revocation and the credential's own scopes still apply. Every automatic approval is recorded as an approval request and as `access_grant_auto` in the audit log. The mode is a private file with no agent-reachable route; a damaged file means ask each time. Switching back to ask stops future automatic approvals but does not revoke grants already given; revoke the agent for that. Residual risk while the mode is on: a prompt-injected agent that holds a send scope can send in any chat it names, so use `--scope` narrowly and prefer ask-each-time for agents that read untrusted content |
| Webhook SSRF | Endpoints are registered only by a human (interactive terminal, typed confirmation; no scope, no API route). HTTPS only. The dialer resolves each name once, refuses the whole answer if any address is loopback, private, link-local (incl. cloud metadata), carrier-grade NAT, multicast, reserved or an IPv4-embedding IPv6 range, and connects to the vetted address, so DNS rebinding cannot change the target. Redirects are never followed and proxy variables are ignored |
| Webhook data egress | Opt-in per endpoint; events carry identifiers only (journal sequence, op, chat ID, message ID, message ref), never bodies or media, so a receiver must hold a scoped read credential to see content. Endpoints can be limited by chat and operation. Residual risk: chat IDs (phone numbers, group IDs) and the fact and timing of activity reach the receiver |
| Forged or replayed webhook requests | HMAC-SHA256 over timestamp and body with a per-endpoint secret, a fresh timestamp on every attempt, a stable event ID for deduplication. Receivers must enforce the five-minute window. The secret is stored in `webhooks.json` (0600) because signing needs it; same trust level as `api.token` |
| Lost or duplicated webhook events | Per-endpoint checkpoint in `webhook-state.json`, advanced only after a 2xx or a recorded dead letter; at-least-once, in order. A position that can no longer be served (restored archive, retention) resets to the journal head and is audited |

## What the human check is, and is not

Until this check existed, "an agent can never approve itself" rested on two soft barriers, and both were tested and found to give way:

- `approve.token` is a 0600 file that any program running as the same user can read (on macOS it now lives in the Keychain instead; see [below](#the-approval-credential-in-the-macos-keychain)). In Codex's default sandbox the loopback API is unreachable, but with network access on, or in full-access mode, a short script that signed a request with that token was accepted by the owner with no terminal and no typed phrase.
- The "interactive terminal" test lives in the command-line client. A pseudo-terminal (for example `script`) satisfies it, so a shell-capable agent could type the phrase itself.

The owner now closes both on macOS and Windows. Every approval of an agent's request, and every choice of "sync all chats", ends in a prompt drawn by the operating system, raised by the owner process whichever way the approval arrived (command line, TUI key press, approval page, direct API call). Creating or revoking an agent credential (`wasync agents grant`, `agents revoke`) asks the same prompt from the command itself after the typed name, because those commands edit `agents.json` directly and work with no owner running. The prompt is the one thing a program running as the user cannot answer: it needs a fingerprint, the account password, or Windows Hello.

| Property | How it holds |
|---|---|
| The prompt says what is being approved | The sentence is built by the owner from its own data: agent name, chosen chat's name from the archive, read or send, history depth, or the destructive action. The agent's own query text is never in it. Names are stripped of control characters and shortened |
| An agent cannot wear the person out with prompts | One prompt at a time; three unconfirmed prompts in ten minutes lock further prompts for five minutes; a request must exist (or the call must be a valid mode change) before any prompt shows |
| "Sync all chats" is still a person's choice | Setting it needs the prompt. Requests it then approves automatically do not prompt again, as before |
| Narrowing mostly does not need the check | Choosing ask-each-time and rejecting a request are safe for an agent to cause, so they do not prompt. Revoking a credential does prompt, because revoking one agent and granting another is how a credential is swapped |
| A notification is only a nudge | It names the agent and says to look; it carries no code, no chat name and no button, and seeing or dismissing it approves nothing |
| The tailnet login header is trusted from loopback | `tailscale serve` strips any client copy of `Tailscale-User-Login` and sets the real one, so a remote device cannot forge it. A program on this computer can reach the loopback port and send the header itself. With the opt-in on, that lets another OS account on the same computer open the web app (read chats, send as the owner), which it otherwise cannot. Same-user programs gain nothing they did not have. The docs say to turn it on only where you are the computer's only user; it is off by default and `wasync tailnet off` ends it at once |
| The approval page is not a boundary | Anything that can reach the loopback listener can open the page (its sign-in link is one-time and short-lived, which is hygiene). A session lasts 30 minutes after its last request and at most 12 hours. A signed-out page on this computer can sign in again only after the system confirmation ("sign in to the wasync web app in this browser"), which a cross-site page cannot start because the listener refuses a foreign Origin; it is not offered through the tailnet, where the Tailscale login signs a browser in. The page forwards an approval to the same owner path, so it still ends in the prompt. Where the computer has no system confirmation the page lists requests but cannot approve |
| The chats pages show message text and attachments | `/ui/chats` lists the chats being synced and shows their recent messages and downloaded attachments, so it is served only to a browser that holds a session from a one-time sign-in link. Anything that can obtain such a link can read what the archive holds, which a program running as the same user could already do by opening the archive file (the same-OS-user line below), so this adds convenience, not capability. `/ui/media` serves a file only for a message whose archived record says it was downloaded, only from inside wasync's media folder, and only if it is a private regular file (0600 on Unix); a sender-chosen name is never used as a path, and the file is sent with `nosniff` and a sandboxing content policy. Asking for a download or changing a chat's download setting there is the same owner action as `wasync media download` or `wasync media policy`. Choosing which chats sync is a capture choice and needs no prompt; agents still see only what they were given |
| Open sending widens where a credential may send | While the person has it on (one hour, after the system confirmation; the web page cannot switch it on where the computer has no confirmation), an agent that already holds the `send` scope may message any chat or number, not only approved chats. Each such message counts against 15 messages and 5 new numbers an hour over all agents, is marked in the sent log and the audit log, and is refused again when the person turns it off or the hour ends. It never gives an agent a scope it does not hold, and agents cannot read or change the switch. Turning it off, or stopping an agent's sending, needs no confirmation because stopping is always safe |
| An approved list widens where one credential may send | The person approves a list of phone numbers for one agent on the Agents page, after the system confirmation that names the agent, the count and the first numbers (the page cannot approve one where the computer has no confirmation). That agent, if it holds `send`, may message those numbers and no others: the 5 to 20 first messages an hour the person chose, spaced at random, three times that in messages, one message per number until it replies, a number that replies STOP, unsubscribe, opt out or the like (any case or punctuation, as whole words) after wasync's first list message to it is dropped from every agent's list and never listed again, a choice `send-lists.json` keeps for good (earlier messages from that number never count, so old chat cannot remove it), and the list ends on the date the person chose. Pausing a list stops its sends and keeps everything else, with no confirmation; resuming it asks again. A removed list's send history is kept for up to 30 days (the oldest numbers go sooner if the file would grow too large), so approving the same numbers again never sends anyone a second first message. Each send is audited as `send_list` and marked in the sent log. A list never gives a scope, another agent cannot use it, and removing it needs no confirmation. A list send turns on capture for that chat, from then on only, so a reply or STOP can be seen; a reply from a number on an active list that arrives in that contact's hidden-ID (`@lid`) chat turns on capture for that chat too, unless the owner turned its capture on or off before, so the owner's choice always wins |
| The web composer sends as the owner | The chats page can send a message you write, to an open chat or a number, through a signed-in page session and its one-time form token. It needs no further confirmation, like `wasync send`: anything that can mint a sign-in link already holds the owner-only approval token, so it could use `wasync send` too. It sends once and redirects, so a reload cannot send it again, and every message is in the sent log with the owner as the sender |
| Waiting requests survive a restart | `pending-approvals.json` is a private file holding only requests still waiting for a person, which expire after 30 minutes. A request that was already being carried out is never restored, so nothing runs twice, and a restored request still ends in the same system confirmation. A damaged or non-private file restores nothing |

Not covered, stated plainly:

- **Code running as the same user that can write the data folder** can still change `access-mode.json` or the agent registry directly, or attach a debugger to the owner. The same-OS-user line above still applies; the sandbox an agent runs in (Codex's default workspace sandbox denies writes outside the workspace) is what holds there. `webhooks add` and `webhooks remove` write their own file from the terminal and still rely on a typed phrase; putting them behind the prompt is planned. The grant and revoke prompts protect the command-line path; they do not stop a program that edits `agents.json` itself, for the same reason.
- **A computer with no system confirmation** (Linux, or a session with no screen) keeps the typed phrase in a terminal as the only check. The owner says so on its first console line, and the approval page shows requests without offering to approve them. Running agents with access to the data folder is not safe there.
- **A person who confirms a prompt without reading it** has approved it. The sentence is deliberately short and specific for that reason.
- **Windows.** The check asks for Windows Hello first (through the PowerShell that ships with Windows). On a computer where Hello is not set up it shows the standard Windows security dialog and accepts only the password of the account wasync runs as (checked with `LogonUser`, and the account that logs on must be the current one). If a dialog cannot be shown or the answer is wrong the approval is refused, never allowed; the typed-phrase-only mode applies only when there is no desktop session at all (for example wasync running as a service). The notification is a tray balloon. All of this builds and is checked by the Windows build, but none of it has been run on a real Windows computer by the author, so treat Windows as untested until someone has walked through an approval there. A Windows Hello PIN is covered by the Hello path; the password dialog does not accept a PIN.

## Setup page and start-at-login

| Property | How it holds |
|---|---|
| The pairing QR code is shown only as an image | The setup page draws it as an image from the code and never prints the code as text, in the page or the logs. The code is useless without the phone it is scanned by |
| A connected agent's secret is never displayed | The owner creates the credential and writes it to the file wasync-axi reads, atomically and privately, then forgets it. If it cannot be saved, the credential is revoked at once. It never replaces an existing saved credential without an explicit tick |
| The page connects read-only agents | An agent connected from the page gets `read.chats` and `read.messages`, on demand and with no expiry, and nothing else; sending, other scopes and expiry need `wasync agents grant` in a terminal |
| Connecting an agent, and installing start-at-login, need the person | Both end in the system prompt, with a sentence built by the owner. Where the computer has no prompt the page offers neither and shows the terminal command, whose own typed confirmation is then the only check (see above) |
| The login item is per user and visible | A macOS LaunchAgent plist or a Windows `Run` value, both for the current account, no administrator rights, removed by `wasync service uninstall` or the page. Installing also starts it now, unless a wasync is already running that the login item did not start, so it never races a wasync the person is running in a terminal. `wasync service restart` stops whichever wasync is running and starts the login item, so an upgraded program takes over |
| The page opens by a link nobody reads | `wasync setup` and `wasync approvals` ask the running owner for a one-time, two-minute link and hand it straight to the browser. It is never printed, so a program that ran the command does not learn it. Anything that can sign with `approve.token` can still ask for one, which is why the page is hygiene and the system prompt is the gate |
| Choosing chats to capture is not agent access | It changes only what is archived on this computer. An agent sees nothing it has not been granted and approved |

Not covered: the Windows login item and prompts are untested on a real Windows computer; Linux has no login item.

## The approval credential in the macOS Keychain

On macOS `approve.token` is no longer a file. wasync keeps it in the login Keychain, and moves an existing file there the first time the owner starts, deleting the file. The Keychain trusts the program that stored it, so a different program that asks for it (an agent running `security find-generic-password`) makes macOS ask for the person's password. This removes the "any program running as you can read the file" weakness at its source; the system prompt above remains the gate and this is a second layer. There is one Keychain item per data directory, and it records that directory so `wasync keychain prune` can remove the ones left by directories that no longer exist. Items made before the directory was recorded are never removed by prune, since a running owner may still depend on one; the person deletes those by hand in Keychain Access. Test binaries are never given the real Keychain unless `WASYNC_TEST_KEYCHAIN=1`.

- It protects the signing credential only. It does not protect files an agent can write (the agent registry, `access-mode.json`).
- **Windows keeps the file.** Windows Credential Manager releases a secret to any program running as the same user without a prompt, so moving it there would add nothing. The Windows Hello or password prompt is the gate there.
- **Unsigned or rebuilt programs.** The Keychain recognises the program by its code signature. The released, signed macOS builds keep their access across upgrades. A build made from source or by Homebrew has no stable signature, so after an upgrade macOS may ask the person once whether wasync may use its own item. That is the same prompt an attacker would see.
- A Keychain read that fails or is denied stops the owner; it never makes a new credential, because that would silently replace the one the commands hold. When the person cancels or denies the prompt (or macOS cannot show it), `serve` exits successfully after one notification that approvals are off until wasync is run again, so the login item does not restart it into the same prompt. The same clean exit happens when macOS refuses to let this build edit an item another build made (error -25244) and wasync cannot replace it; the notification names the item to delete in Keychain Access. Any other Keychain failure still exits with an error.
- A person who clicks Allow on a Keychain prompt they did not expect has given the credential away, which is why the approval still needs the system prompt on top.

## The tool server and the Codex plugin

See [ADR-003](ADR-003-mcp-tool-server.md). `wasync-axi mcp` serves tools over standard input and output for apps that have no terminal.

| Property | How it holds |
|---|---|
| The tool server cannot approve, grant or reveal | The menu has no such tool, and a test fixes the exact list. Asking for a chat (`whatsapp_request_access`) queues a request the person answers on their own computer; the server never sees the answer's secret and approving still ends in the system prompt |
| The tool server adds no authority | Each tool runs a `wasync-axi` command with fixed flags. Every value is a separate argument. Positional values (search text, chat, message ref, emoji) come after `--`, so text that looks like a flag is only text there. Values of fixed flags (`--text`, `--mentions`, `--match`, `--chat`, `--cursor`, `--consumer`, `--after`) come before `--`: they still reach the command whole, but a value of exactly `--json` switches that command's output to JSON. That changes only the output format, never the authority. Arguments a tool does not declare, over-long text, non-integers and missing fields are refused before any command runs |
| It cannot corrupt its own protocol stream | Each command writes to its own buffer and has no access to the input channel; replies are one JSON line each |
| Message content stays data | Tool results are the same delimited output as the command line, and the plugin's skills tell the agent to treat message text, contact names and group names as untrusted |
| Starting setup is bounded | One tool runs `wasync setup` detached, no arguments, output discarded, at most once per thirty seconds; the page it opens needs the person (ADR-003). It cannot be steered to open anything else |
| Writes keep Codex's own approval | Reply, react and edit are marked as not read-only (edit as destructive) so Codex's tool-approval modes can add a prompt of their own; wasync still requires the granted scope and an approved chat |

Not covered: if the Codex app launches the tool server with a PATH that lacks `whatsapp-axi`, the plugin does not start (it fails closed). A prompt-injected agent can still open the setup page once per thirty seconds and can send a message where a send scope and an approved chat already exist; narrow scopes and Codex's per-tool approval are the controls there.
